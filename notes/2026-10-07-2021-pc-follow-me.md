(`2026-09-24-win-follow-me-plan.md`, `-HANDOFF.md`, `-DEPLOY-HANDOFF.md`) with what is
live and verified today. All code is on branch `duck-deeper`. It is not merged to `master`.

## How it works
- **Playback bus (server, live on :8100).** Every renderer long-polls
  `GET /api/playback/command/next`. The phone polls with no params and is the `phone` device.
  A PC sends `?device_id=pc-solace&device_name=Solace&device_type=windows`. One device is
  *active*, and bus commands go only to it. When nothing is declared active, the phone is the
  renderer, so phone-alone behavior is unchanged.
- **Transfer = handshake.** `POST /api/playback/devices/{id}/activate` (also `dj_transfer` in
  the DJ MCP and "Transfer here" in the tray) sends the old device a `deactivate`. It pauses,
  posts its exact state and acks. The new device then gets an `activate` with the queue from
  the current track on, plus the position. An audiobook travels as `book_id` + book-global
  position (#2680). A stale old device (asleep PC) is skipped: the handoff goes straight from
  its last report.
- **PC client** (`windows_client/audiplex_pc`): a tray icon with no window. Left-click opens a
  small now-playing/transfer window. VLC plays through a loopback proxy that adds the Bearer
  token, and range requests work so seeking works. It has crossfade, the sleep bed (#3435),
  and audiobooks with progress synced to the phone (#2680).
- **Phone**: the handshake is in `DjCommandClient.kt` (`deactivate`/`activate`), shipped in
  APK v55. **No phone change was needed for this.**

## How Todd tries it (on Solace)
1. Start the client: double-click nothing yet. From `Q:\Development\audiplex\windows_client`,
   run `pythonw -m audiplex_pc`. A tray icon appears. Its config is already in
   `%APPDATA%\AudiplexPC\config.json` (pc-solace token, server http://192.168.50.139:8100).
2. Play something on the phone as usual.
3. Move it to the PC by any of these:
   - click the tray icon, then **Transfer here**;
   - or tell the DJ "play it on Solace" (`dj_transfer("Solace")`).
   The phone pauses, and Solace picks up the same track, position and queue (or the same
   audiobook spot).
4. Going back: tell the DJ "back to the phone", or use the tray window's transfer-to-phone.
   The PC pauses and the phone resumes where the PC was.
5. To check it without listening: `dj_devices` / `dj_now_playing` show which device is active.
   The log is at `%APPDATA%\AudiplexPC\audiplex_pc.log`.

## Open items (not done here)
- **Autostart** on Solace/Athena: waiting on Todd's OK (rider R3).
- **Athena**: needs its own token: `cd server && python -m audiplex.create_service_token --username pc-athena`.
- **Auto-follow** (moving by itself when Todd sits at a PC) is not built. Transfer is one tap or one sentence.
- **Media keys / Windows media overlay (SMTC)**: follow-up. The research says to use the
  `winrt-Windows.Media.Playback` `MediaPlayer().system_media_transport_controls` route, about
  100 lines in an isolated `media_keys.py`, hooked to `Player.toggle/skip/previous` and
  `state()`. It needs winrt wheels, which are not installed, and global pip is blocked, so the
  client would have to move to a venv. The no-install fallback is `RegisterHotKey` for
  VK_MEDIA_* through pywin32 (about 50 lines). That gives no overlay and fights other apps
  for the keys.
- **Edge case found by the e2e: transferring right after a resume can start paused.**
  `transfer()` reads `was_playing` from the old device's last state report, and the PC reports
  only every 5 s. A transfer within about 5 s of a PC resume therefore carries `playing=false`.
  The fix is for the PC bus to post state immediately after executing a play/resume command
  (or after any command). That change is small, but not done here.
